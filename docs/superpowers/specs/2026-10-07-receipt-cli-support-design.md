# Generic workflow analysis, test planning and isolated execution

Status: approved by the owner on 2026-10-07; implementation plan requested. No CLI extension implementation has started.

## Purpose and current evidence

Given any new workflow export, analyze its structure and dependencies, determine what can be tested, produce a concrete test plan and execute qualified tests in an isolated runtime. Keep workflow-specific contracts/fixtures in separately maintained projects. Add generic file intake, reviewed Code, PDF extraction and native table support, an automatically managed Docker n8n runtime and selectable deterministic/mock, local-model and replay modes for LLM dependencies. The receipt workflow is the first external acceptance target, not a feature or domain of the CLI. This extends the existing compiler, runtime adapters, gateway, evidence assertions and ownership journal; it does not introduce another orchestration service or involve Grid.

## Repository and domain boundary

The owner clarified that the CLI and its repository should remain generic. Current `src/` has no receipt-specific business logic, but receipt building/validation/provisioning code currently lives under `examples/receipt-intake/`, and two top-level test files import it. Separate those assets into an independent workflow/test project before implementing generic runtime support. Preserve their Git history/evidence, exact live-resource ownership records and private secret-file permissions; do not delete or reprovision the existing live resources during relocation.

The independent project owns its workflow JSON, node business code, receipt schema, extraction prompts, provider selection, destination mapping, synthetic documents, expected values, domain tests, live provisioning/lifecycle scripts and verification evidence. It invokes wfcheck like any other consumer. Its suite explicitly supplies generic fixture paths, HTTP mock bindings, isolated table schemas/seeds and assertions. The CLI must not import that project's modules or detect it by name, filenames, node names, columns or resource IDs.

The CLI owns generic export validation/inspection, node type/version/operation support, input transports, mock matching, credential/table isolation, execution correlation, assertions, reports and exact-ID recovery. `src/`, CLI configuration and suite schemas must contain no receipt fields, money/date rules, OCR prompts, Yolo endpoint, Grid coupling or application-specific IDs. Limits and trust policies apply consistently to every project. Do not introduce a receipt-specific CLI command, plugin, profile or conditional branch.

CLI tests use small domain-neutral workflows to prove Form upload, Code execution, PDF extraction, HTTP substitution and table evidence/cleanup. Keep domain assertions and tests in the independent project. The existing generic demonstration workflows can remain as examples; `wfcheck init` and the package must not distribute the receipt application's deployment code or live resource configuration. Prove the new capability against both the independent receipt project and an unrelated minimal workflow so generic support is demonstrated rather than inferred.

## Choice

A permissive node allowlist would allow unintended real writes and provider calls. An LLM-only planner could misclassify dependencies or invent expected results. The recommended architecture is deterministic analysis and plan validation, with optional LLM assistance for proposals, followed by explicit runtime/node adapters and disposable resources. The current restrictive execution profile remains the default, and existing suites remain compatible.

## New workflow onboarding and planning

The public entry point is a workflow export, not an application profile or a handcrafted list of known node names. `wfcheck inspect workflow.json` inventories capabilities and gaps. Add `wfcheck plan workflow.json --out suite.yaml` to produce a versioned draft suite and a structured analysis report. An optional `--requirements requirements.md` supplies the independent behavior contract; `--assist local --model MODEL` enables the local planning assistant. These commands are separate from `--llm mock|local|replay`, which selects how the *workflow's own* LLM dependencies behave during execution.

The deterministic analyzer parses all node identities/types/versions/operations, main and AI connection types, selected triggers, branches, error paths, retries, credential references, literal destinations, file/binary parameters, declared output schemas and supported expression references. Obtain node descriptions/schema metadata from the selected pinned n8n runtime or a versioned catalog when available; never fetch or install arbitrary community packages because an export references them. Runtime metadata describes node configuration; it does not prove complete input/output or side-effect semantics. Apply generic node adapters/capability descriptors keyed by type, version and operation to classify test drivers and effects: pure transform, dependency read, LLM, destination write, durable state, clock/wait, sub-workflow or opaque executable behavior. Expressions or Code whose effects cannot be resolved statically remain explicitly unknown rather than being executed during analysis.

Keep general graph analysis separate from execution eligibility. An unknown node does not stop the inventory of the rest of a workflow. Analysis can accept/report arbitrary graph topology while execution validates its supported trigger selection, connection types, cycle/iteration budget and node capabilities. Build a capability registry with analyzed, executable, mockable, observable and isolatable states instead of one Boolean allowlist. Known adapters drive fixtures, request protocols, runtime provisioning and evidence assertions; unsupported integrations require an adapter or explicit trusted binding and are reported by stable node ID. Agnostic means no business-domain coupling, not a claim that every n8n integration can already be safely executed.

The plan records source hash, runtime/image/catalog identities, selected entry point and driver, input schema/fixture requirements, dependency policies, mock/local/replay bindings, isolated resource schemas/seeds, Code trust requirements, scenarios, assertions and unresolved items. Every conclusion records its source JSON path/catalog/requirement and whether it is deterministic, inferred, user-supplied or unknown. Distinguish required configuration from unsupported runtime/adapter features. Determine readiness with deterministic rules: unknown external effects, unresolved credentials/bindings, missing required fixtures or missing execution support cannot produce a ready-for-run plan.

Generate candidate inputs and branch/error cases from explicit schemas and supported conditions, including missing/invalid input, dependency errors and bounded retries. Suggest duplicate/idempotency cases only where a declared identity/upsert contract supports them; do not invent application behavior from node names. Propose synthetic response fixtures with the protocol shape and fields demanded by known downstream references, but mark fabricated example values as drafts. Do not use a workflow's pinned data as independent expected truth or pass because a node was skipped.

The optional local LLM receives a bounded, sanitized analysis projection plus explicitly included Code/requirements when requested, and returns schema-validated proposals: inferred business intent, fixture candidates, ambiguous mappings, expected structures and missing adapter/configuration explanations. Workflow text, prompts, comments and Code are untrusted source data for this assistant. It has no Docker, filesystem-write, API-key, credential or workflow-execution tools. It cannot authorize effects, modify source code, invent credentials, override deterministic capability checks or promote its suggestions into accepted expectations. Revalidate every proposal through the same plan compiler; deterministic facts take precedence over model guesses. Local-only model selection and no hosted fallback apply to the assistant too. Record model/settings and proposal provenance.

An exported workflow tells the tool what it currently does, not necessarily what it should do. Automatically generated execution/protocol/schema/isolation checks are useful, but do not establish business correctness. Expected outputs come from independent user/project requirements and authored fixtures, or an explicitly reviewed recorded baseline for regression comparison. A baseline proves preservation, not correctness. Report smoke/integration evidence, approved regression expectations and independently specified behavioral assertions separately; never label an automatically guessed suite as semantic verification. The generated suite is ordinary editable project data, and repeat runs need no analyzer/model call once it has been reviewed and completed.

For a new workflow, the intended user path is: export -> inspect/plan -> supply only listed missing fixtures/contracts/bindings -> run against disposable Docker with selected LLM mode -> inspect actual outputs, dependency requests, isolated writes and assertion results. Source workflow stays unchanged; no receipt knowledge is needed. An opt-in automatic smoke mode may execute only a fully isolated supported plan under its explicit test policy and must report that behavior expectations were not independently supplied.

## Automatically managed local runtime

Add `--runtime docker|cloud`, preserving existing Cloud behavior when not selected. Docker mode owns startup, readiness, workflow/resource provisioning, execution, evidence and teardown. Use an official n8n image with an explicit tested version and resolved digest, never an unrecorded `latest` tag. A project may override the supported image pin in trusted configuration; discovery reports image/version/capability mismatches before workflow execution. Pull the pinned image when necessary, without installing or updating the host Docker daemon. No n8n Cloud API key or HTTPS tunnel is required for local mode.

Create a new private volume and scoped network per run; publish only a dynamically assigned loopback port. Start only n8n, its required version-matched Code task runner and the test gateway, without n8n Assistant, web-search services, Docker-in-Docker or privileged containers. Workflows never receive the host Docker socket, arbitrary host mounts or the controller's secrets. SQLite is sufficient for disposable single-process tests; queue mode and Postgres are not required. Enforce bounded CPU/memory, startup time, execution count and shutdown. Journal exact container/network/volume IDs before importing workflows and clean only those IDs; do not prune Docker globally. Retain shared downloaded images as an explicit reusable cache, not an unreported leftover service.

Fully automatic first-run owner/API setup is a qualification gate, not an assumption. First verify a supported bootstrap for the selected image using documented server CLI import/setup operations in the fresh owned volume, followed by public API discovery, or documented CLI execution with complete actual execution evidence. A version-specific minimal synthetic owner/API seed imported through the documented entity CLI may be used only in the new owned runtime, with generated ephemeral secrets and a checked schema/version. Do not call private editor APIs or write arbitrary SQL to bypass setup. If the selected image cannot bootstrap unattended through those boundaries, report the missing supported step instead of calling startup fully automatic. CLI execution must not silently substitute for Form/Webhook trigger fidelity: transport substitutions and evidence limitations must be explicit.

Put n8n and the Code runner on an internal test network and route dependencies through the gateway. Only the gateway may have a controlled connection to the configured local model service; it must not offer an arbitrary forward-proxy route. Keep external APIs mocked unless a dependency is explicitly configured through the existing trusted test bindings. Prove direct IPv4/IPv6/DNS egress behavior and model reachability before claiming containment; a generic Docker bridge alone does not establish it. Isolated runtime behavior is recorded separately from Cloud fidelity. Keep an opt-in failure-debug retention mode with exact-ID cleanup instructions; normal runs and interrupts tear down automatically.

## Dynamic LLM detection and explicit modes

Add `--llm mock|local|replay` and the same versioned suite configuration, with deterministic `mock` as the default. Flag precedence is explicit and the effective mode is recorded before executing. `inspect` discovers supported native model node types/versions and explicitly bound HTTP model calls, lists planned substitutions by stable node ID and identifies unsupported providers/features. Detection uses supported integration/operation semantics and literal trusted bindings, not receipt-specific names or a guess based on arbitrary URL fragments. A changed/dynamic destination or unrecognized integration fails closed. An `auto` discovery option can select from compatible *installed local* models using trusted preferences and reported capabilities, then freezes the choice for the entire run; it must not silently change provider/model mid-test.

In `mock`, ordered fixture responses deterministically exercise success, refusal, invalid structure, timeout and error paths; no inference service is required. In `local`, forward only matched LLM requests to the configured Ollama or OpenAI-compatible local endpoint, replace real provider credentials with test-only credentials, adapt supported request/response shapes and preserve prompts/messages. Initially qualify non-streaming OpenAI-compatible chat through HTTP nodes and a supported native OpenAI Chat Model integration. Unsupported Anthropic/Responses/streaming/embedding/tool/vision combinations remain explicit gaps until their protocol and native-node tests exist; do not represent one chat endpoint as universal LLM support. Native model connection types must be validated explicitly in the workflow graph.

On Apple Silicon reuse the already-running native model service when selected; do not force inference into a CPU-only Docker container. Offer a separately pinned Ollama container for Linux/CI as an opt-in managed service when no host service is intended. Do not download new models, modify installed models or switch other applications' routing automatically. Local-mode discovery rejects models with remote/cloud backing (including `remote_host` metadata), validates configured endpoint/capabilities and does not forward incoming provider authorization, account IDs or API keys. Unsupported or unavailable local models cause a test error; never fall back to hosted inference. Endpoint selection comes only from trusted configuration.

Bound inference time, calls, request/response size, context/output tokens and agent iterations. Model-returned tool calls are data consumed by the workflow; the gateway itself does not execute tools. Record model name/digest, runtime version, effective generation settings, prompt/request and response hashes, duration and actual observed outputs. Temperature/seed controls are best-effort and do not make model mode deterministic. Reports label model-backed runs distinctly. `replay` matches versioned request hashes to human-approved synthetic recordings and fails on misses; recording is explicit, private by default, and never rewrites expected values or silently promotes model output into regression truth.

## Inspection and compilation

Add `wfcheck inspect <workflow>` with console and JSON output. It requires no API key, starts no tunnel and performs no Cloud operations. Report all gaps with stable node IDs, versions and paths, source hash, Code hashes, credential-reference presence and required isolation bindings. Do not print Code, receipt contents, credential payloads or arbitrary exported metadata. Unknown or malformed constructs must not produce a runnable verdict. Distinguish runnable, configuration needed and unsupported; unsupported inspection exits 2.

Accept known normal public-export metadata only by projecting the runtime fields used to create a new workflow. Never copy IDs, account sharing, active versions, pinned outputs or static state into the test copy. Keep unknown runtime fields/operations rejected. Preserve the original source bytes and report their hash and every transport/configuration transformation.

Add an optional reviewed-workflow profile to the versioned suite schema. It pins the exact source hash and explicitly opts into executing its reviewed Code and expressions in n8n Cloud. A changed export fails preflight until its pin is deliberately reviewed and updated. Validate an acyclic, reachable graph and supported node versions/parameter shapes even in this profile. The first supported additions are Form Trigger 2.2 (one required file field), JavaScript Code 2, PDF Extract From File 1, Data Table 1 row get/upsert, the existing If 2.2 operations and HTTP Request 4.2 with JSON object bodies. No executable suite hooks, arbitrary node types, schedules, sub-workflows, shell operations or arbitrary credentials are enabled.

This trust profile is an explicit security change: reviewed Code and expressions execute as authored on the Cloud instance. A hash pin prevents unnoticed changes; it is not a code sandbox or an egress firewall. Inspect and documentation must state that limitation. Do not claim that HTTP bindings intercept outbound requests made directly by Code.

## File trigger and HTTP mocks

File fixtures are explicit suite inputs with a repository-contained path, expected field name and MIME/type. Bound and byte-check reads, reject symlink/path escape, upload one file, preserve its bytes and hash, and record its hash in reports. Keep existing JSON Webhook input behavior. Use a fresh marker in the uploaded filename for Form execution correlation; verify both the owned workflow ID and the marker in the saved trigger binary metadata, including execution detail. Do not select an execution merely because it is newest.

Create a fresh Basic Auth credential for each temporary Form workflow through documented public API operations. Keep its random password in private runtime state, redact it, and authenticate the upload. Do not reuse or read the production Form credential. Publish briefly and trigger exactly once; no automatic trigger retries.

Every native HTTP node must have an explicit stable-node binding with the expected original literal URL and the gateway mock path. Reject dynamic destinations, missing bindings, conflicting bindings and unexpected credential types. In the test copy strip the provider credential and original auth configuration, substitute the authenticated gateway URL, disable redirects, and bound timeouts/retries. Never read/use the Yolo key or call Yolo during regression runs. Keep request JSON semantics intact. Existing fake-header placeholder workflows continue to work.

Keep the current 64 KiB gateway body limit for this initial slice and reject file fixtures that cannot fit the supported request budget; this is a generic limit, not an application-specific exception. Do not silently raise all gateway limits to accommodate large images. Exclude inline binary data URLs and binary payloads from persisted reports while retaining hashes/sizes and the structured observations needed for assertions. This is an evidence-format change, not a claim that arbitrary customer data is sanitized.

## Native table isolation, evidence and cleanup

The profile declares logical test tables, explicit column types, bounded synthetic seed rows and the native nodes that use each table. Check the binding against each node's original table reference and explicit mapping before import. Create fresh task-owned tables through the public API and remap all table references to their exact new IDs. Never write to/read the live receipt table as part of a regression case. Execute native row get/upsert rather than replacing their behavior with a Code simulation.

Read actual table rows through the public API after terminal execution and before cleanup. Add table row-count and stable-key row-field assertions. Missing or paginated/incomplete evidence is an error, never an empty successful result. A seeded duplicate case must preserve the existing row and manual notes while skipping both model calls. A native write-failure case can use an explicitly declared fault binding to a separately created, then deleted, exact owned table; no arbitrary real destination ID is allowed for fault injection.

Extend the private ownership journal to workflows, executions, generated credentials and tables with creation intents and exact IDs. Persist ownership immediately after each creation; an uncertain create remains a reported recovery intent. Clean executions/workflow before removing referenced credentials/tables. Verify recorded names and instance before destructive operations, tolerate confirmed absence, and retain all unresolved resources in the recovery manifest. Clean resources created before a workflow import fails, too. Never search/delete by prefix. Extend `wfcheck cleanup` to recover the new resource kinds and old manifests.

## Exclusions and follow-ups

No Grid changes, new OCR stack, receipt approval/delivery features, real patient data, provider credential purchases, changes to existing n8n/Docker/model-service accounts, permanent ingress or public releases. Setup in the new disposable local instance is owned by the CLI. No universal integration interception or unverified network containment claims. Large binary request support, scan-only PDF rendering, simultaneous duplicate uploads, table timeout reconciliation and additional native/provider integrations remain explicit follow-ups rather than unsupported features marked passing.
